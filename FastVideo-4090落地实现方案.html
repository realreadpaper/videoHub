FastVideo on RTX 4090 — 落地实现方案

从裸机到对外提供视频生成服务，逐条命令。基于 hao-ai-lab/FastVideo main 分支 commit 9b0e57fe 实测核对。

4090 官方支持 单卡 24 GB 96 GB 内存 环境必须 Linux / WSL Python 3.10–3.12

0方案总览

目标不是"跑个 demo"，是建成一条能持续出片、能对外提供接口的生成链路。拆成三个里程碑，每个都有明确验收标准，任何一步不通过就不往下走。

M1 · 跑通
环境就绪，跑出第一个 MP4，确认卡和驱动没问题
验收：video_samples/ 下有可播放 mp4
M2 · 调优
叠上 FP8 + 稀疏注意力 + 逐层卸载，摸清这张卡的真实产能
验收：拿到单条出片耗时基线
M3 · 服务化
起 OpenAI 兼容 API，任何 OpenAI SDK 客户端可直接调
验收：curl 拿到 MP4 + 压测有数

1M1 · 环境准备与跑通

两条路。Docker 快但代码是只读习惯，源码装可改代码。第一次建议走 Docker 先把链路验通，要改代码再转源码。

路线 A：Docker（推荐起步，约 30 分钟）

# 1) 宿主机确认 —— 必须能看到卡，看不到就先修驱动
nvidia-smi
docker --version
nvidia-container-toolkit 状态检查   # 没装见下

# 2) 拉镜像（约 15 GB，第一次慢）
docker pull ghcr.io/hao-ai-lab/fastvideo/fastvideo-dev:py3.12-latest

# 3) 起容器 —— 三个挂载点很关键，尤其模型缓存
mkdir -p ~/fastvideo_models ~/fastvideo_outputs
docker run --gpus all -it --rm \
  -v ~/fastvideo_models:/root/.cache/huggingface \
  -v ~/fastvideo_outputs:/outputs \
  --shm-size=16g \
  ghcr.io/hao-ai-lab/fastvideo/fastvideo-dev:py3.12-latest
为什么这三个参数不能省：
· -v .../huggingface —— 不挂载的话，容器一删模型权重全没，几十 GB 重下
· --shm-size=16g —— Docker 默认共享内存只有 64 MB，多进程加载会直接崩
· --gpus all —— 需要宿主机装好 nvidia-container-toolkit，否则报 could not select device driver

容器内代码在 /FastVideo，虚拟环境已激活。

路线 B：源码安装（要改代码时用）

# 1) 装 uv（比 pip 快且稳，官方推荐）
curl -LsSf https://astral.sh/uv/install.sh | sh
source ~/.local/bin/env

# 2) 拉代码
git clone https://github.com/hao-ai-lab/FastVideo.git && cd FastVideo

# 3) 建环境 —— Python 必须 3.12，别用系统的
uv venv --python 3.12 --seed
source .venv/bin/activate

# 4) 装 FastVideo（CUDA 12；若是 CUDA 13 换成 cu130）
UV_TORCH_BACKEND=cu126 uv pip install -e .

# 5) 可选但推荐：装 FlashAttention，快一档
uv pip install flash-attn --no-build-isolation -v

关于 VSA 稀疏注意力的内核

4090 不是 Hopper，fastvideo-kernel 会跳过 C++（ThunderKittens）编译，只装带 Triton 内核的 Python 包。这是官方设计好的降级路径，功能可用。如果启动时报 VSA 相关错误，先退回 FLASH_ATTN 跑通，再回来排查内核。

验收：确认卡被正确识别

python -c "
import torch
print('torch ', torch.__version__, '| cuda', torch.version.cuda)
print('gpu   ', torch.cuda.get_device_name(0))
print('cap   ', torch.cuda.get_device_capability(0))
print('vram  ', round(torch.cuda.get_device_properties(0).total_memory/1024**3, 1), 'GB')
"
# 期望输出：
# torch  2.12.0+cu126 | cuda 12.6
# gpu    NVIDIA GeForce RTX 4090
# cap    (8, 9)          ← 必须是 (8,9)，这是所有优化的判断依据
# vram   24.0 GB

跑第一个样片

# 用仓库自带的最小例子：Wan2.1 T2V 1.3B，480P，自动下权重
python examples/inference/basic/basic.py
首次耗时
下权重 5–15 分钟（看带宽，约 6 GB）+ 加载 1–2 分钟 + 生成 81 帧约 1–3 分钟
产物位置
video_samples/ 下的 mp4，脚本会连续生成两条
同时监控
另开终端 nvidia-smi dmon -s um -c 120 看显存与利用率曲线

如果这一步就 OOM

1.3B 在 24 GB 上不该 OOM。真发生了，按顺序排查：

  • 显存被别的东西占了 —— nvidia-smi 看有没有残留进程
  • 换更保守的配置：直接用下一节的 06 号模板（已带 FP8 + 卸载）
  • 分辨率降到 640×384、帧数降到 49

2M2 · 叠上 4090 的优化

三个优化都在 4090 的架构支持范围内，叠起来才压得出产能。

优化开关4090 上的作用
FP8 权重量化engine.quantization.transformer_quant: FP8DiT 权重砍一半，官方把 4090 与 H100、L40S 并列点名为支持设备
VSA 稀疏注意力FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN
+ pipeline.experimental.VSA_sparsity		跳掉大部分注意力块计算，长视频序列上省显存也提速
DiT 逐层卸载engine.offload.dit_layerwise: true权重逐层过 PCIe，与计算重叠，开销可忽略 —— 单卡的显存续命线
# 用 06 号模板：1.3B + FP8 + VSA 0.8 + 逐层卸载
FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN \
  fastvideo generate --config fastvideo-configs/06-rtx4090-24gb-fp8-vsa.yaml

要摸清产能，先跑标准压测

# 关掉编译，重复跑 N 次取平均 —— 首次生成永远最慢，别拿它当基线
# 记录：单条出片秒数、峰值显存、GPU 利用率
nvidia-smi dmon -s um -c 600 > gpu_log.txt &
FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN \
  fastvideo generate --config fastvideo-configs/06-rtx4090-24gb-fp8-vsa.yaml

# 跑完后看峰值显存：
awk '{print $3}' gpu_log.txt | sort -n | tail -1

为什么强调"别拿第一次当基线"

开了 torch.compile 后，首次生成要等几十秒到几分钟建图，这是一次性成本。官方文档专门点出："测量预热轮是最常见的得出『编译反而更慢』错误结论的原因"。测速必须丢掉第一轮。

升级到 14B（压榨这一步的极限）

官方 main 分支里本身就带一份单卡 14B 480P 的配置，所以这条路是官方承认的。用 07 号模板：

FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN \
  fastvideo generate --config fastvideo-configs/07-rtx4090-24gb-14b-push.yaml

三个开关少一个都可能崩：FP8 压权重、VSA 砍注意力、逐层卸载把权重挪到宿主内存。96 GB 内存在这里才真正派上用场。

3M3 · 服务化：对外提供接口

这是变现的关键一步。FastVideo 自带 OpenAI 兼容的 REST 服务，起来之后任何 OpenAI SDK 的客户端都能直接调，不用写适配层。

# 启动服务（用 08 号配置：单卡 4090，已开 FP8 + VSA + 编译）
FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN \
  fastvideo serve --config fastvideo-configs/08-4090-serve-fastwan1.3b.yaml

服务暴露的接口

接口方法用途
/playground/GET浏览器里的可视化生成界面，起服务后直接开
/v1/modelsGET列出可用模型（OpenAI 标准）
/v1/videosPOST提交生成任务，返回任务 ID（异步，需轮询）
/v1/videos/syncPOST阻塞式，直接把 MP4 二进制吐回来
/v1/imagesPOST文生图模型用（SD3.5 / FLUX 等）

验证：三条命令确认服务可用

# 1) 浏览器打开可视化界面
open http://127.0.0.1:8000/playground/

# 2) 命令行拿一条视频（同步接口，最直接）
curl -X POST http://127.0.0.1:8000/v1/videos/sync \
  -H "Content-Type: application/json" \
  -d '{"model":"fastwan21-1.3b","prompt":"a raccoon peers through sunflowers, cinematic"}' \
  -o test.mp4
ffplay test.mp4

# 3) 用官方客户端脚本（验证 OpenAI SDK 兼容性）
FASTVIDEO_BASE_URL=http://127.0.0.1:8000 \
FASTVIDEO_MODEL=fastwan21-1.3b \
python examples/serving/clients/video.py

压测拿并发上限

# 另开终端，服务保持运行
fastvideo bench --dataset vbench --num-prompts 20 --port 8000

这个数字决定你能承诺给客户多少并发 —— 单卡 4090 的并发上限通常很低，先测出来再谈。

⚠️ 对外暴露前必须加鉴权

官方文档明确写：客户端 SDK 里的 key 只是占位符，不是认证机制，并建议"把服务保持在回环地址，或使用带认证的反向代理"。所以配置里我写的是 127.0.0.1。要对外提供服务，必须自己套一层 Nginx / Caddy + API Key 校验。直接改 0.0.0.0 裸奔，等于把你家 GPU 挂公网给人白嫖。

4变现路径

服务化打通后，实际可变现的三条路，按落地难度排序：

路径怎么做关键前提
① 自用内容生产
最快		 把 3 步蒸馏模型当成素材机：一条 prompt 批量出 480P 镜头，进你的解说/短剧剪辑管线。/v1/videos/sync 天然适合脚本化批处理 先测出单条耗时，算清"一小时能出几条"
② 私有化交付
中等		 给客户部署一套本地视频生成服务。客户自己有卡，你卖部署 + 调优 + 工作流 把 M1–M3 流程整理成可交付的安装包
③ API 转售
最难		 起服务对外按次计费 单卡产能太低，且需核清权重许可 —— 见下

许可红线（踩了就是法律风险）

FastVideo 代码是 Apache-2.0，但权重是各自独立的许可：

  • Wan 系列 → 跟随各自 model card，商用前逐一核对
  • MiniMax H3 系列 → MiniMax H3 Community License，与 Apache-2.0 无关
  • Lucy Edit Dev → 明确非商用

拿代码做内部产品没问题；对外卖服务前，必须逐张核对你要用的那个模型权重。这一条不是建议，是硬约束。

5排错速查

症状原因处理
could not select device driver缺 nvidia-container-toolkit宿主机装 toolkit 后重启 docker 服务
加载阶段就崩 / 卡死Docker 共享内存不足加 --shm-size=16g
Invalid argument 类 CUDA 错误pinned memory 分配失败offload.pin_cpu_memory: false（官方在 4090 的例子里正是这么注释的）
VSA 启动报错Triton 内核未就绪退回 FASTVIDEO_ATTENTION_BACKEND=FLASH_ATTN 先跑通
换了后端却不生效后端只解析一次改 FASTVIDEO_ATTENTION_BACKEND 后必须重建生成器 / 重启进程
experimental 里的键改了没用该字段无 schema，键名错会静默失效对照官方配置原文逐个核对拼写
选了量化但没变快NVFP4 在 4090 上会静默回退 FA4090 只能用 FP8，NVFP4 是 sm_120 硬门槛
编译后反而变慢把预热轮算进平均了丢掉第一次生成再测
