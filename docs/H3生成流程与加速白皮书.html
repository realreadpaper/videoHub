一、总览：三个角色与一条数据链

这套系统里只有一台机器在算视频，另一台负责"想"。分工是一条清晰的线：

角色在哪负责不负责
编排端本机 macOS 拆解参考片、写剧本与提示词、制备参考帧/音频、生成工作流 JSON、回收审查、拼片、外挂字幕、剪映终稿 任何 GPU 计算（不要在本机装 torch）
生产端GPU 服务器 ComfyUI 引擎 + 6 个权重 + 队列 worker + 出成片 不做创意决策；产出直接落盘，无后处理
接口两者之间 wf_*.json（几 KB）+ 输入资产（wav/jpg）上行；*.mp4 下行 不是代码同步、不是共享文件系统
★ 一句话理解产能

服务器侧是一条串行队列：一镜跑完才轮下一镜。所以「快」只有两种来源 —— ①让每一镜更短（帧数、步数、算子），②根本不要等（多实例并行 / 不要空转 / 不要在冷启上重复付费）。 这份文档后面的四层加速，全部落在这两件事上。

S0–S1 · 切分单位选错，后面全白干

这是整条链上唯一一处在"上 GPU 之前"就能把成本砍掉一半的决策。

症状：用户反馈「一镜 15 秒，5 秒一个动作，太缓慢了」。
根因不是 prompt 写坏了，是切分单位错了 —— 按"镜"切，原片一个 15 秒长镜里其实只有一件事 （「往楼上走」），模型 5 秒演完，剩下 10 秒只能原地磨。

改成 「1 句台词 = 1 个生成单元」。判据来自实测：

实测项04 面试三试05 相亲测试含义
原片镜数 / 台词句数113 / 68128 / 72镜比句多一半 —— 大量镜是硬切出来的
语音覆盖片长99.7%96.6%几乎全片都在说话
句间间隙中位0.00 s句边界 = 说话人边界 = 语义边界 = 气口边界

三点好处：① 一句话一个人一条连续语音 → 原声锁天然成立，不串 voice； ② 句长中位 3.6 s，吸附栅格后正是「一镜 4 秒」的节奏； ③ 台词照抄原片 → 剧情一字不改。

★ 成本反直觉：切短不但治拖沓，还更省机时

因为单镜耗时是帧数的平方级函数（注意力 O(N²)）—— 22 帧 ≈ 19 s 机时/秒视频，354 帧 ≈ 38 s 机时/秒视频。 短视频每秒便宜一半。所以「切短」没有任何取舍，是纯赚。

但有两条例外不能碰：

  • 1.6 s 的短单元不可合并 —— 它们是反应句/金句（「这什么味儿啊？」），是节奏的命门。 质量安全下限 39 帧 = 1.63 s；22 帧 = 0.92 s 有风险，脚本默认抬到 39。
  • ASR 会把相邻说话人并进同一句 —— 必须人工拆。复核范围有界：只看 ≥5.0 s 的单元 （实测占 1/3）。判据：① 一句里「问完接着答」→ 换人；② 句中称呼突变 → 换人。 这就是全流程里真正需要人的那一处 —— 脚本能切到句，但谁在说话要人判。

S2 · 参考帧必须零文字（踩过的最贵的坑）

★★ 模型会把参考帧里的硬字幕"原样画进"成片 —— 这不是幻觉，是搬运

2026-09-19 试拍 4 条，4/4 全部带烧死字幕：台词条乱码、底部「剧情演绎 无不良引导 请勿模仿」、 左下角红色下箭头。病根是参考帧自身带字（原片帧 94–96% 带文字）。

所以「参考帧零文字」是复刻的前置条件，不是优化项。

判别方法（先分辨是"泄漏"还是"幻觉"，别一律怪模型）：

# 量字幕带 edge = mean|Laplacian| 与黄字像素占比
python3 _remake/check_band.py            # 参考帧带内偏高 = 泄漏
python3 _remake/check_burn_in.py         # 成片被烧字（幻觉 or 泄漏）
python3 _remake/check_refs_all.py        # 全量扫：字幕带 y 870–1010 是否还有字

现行解法 rescrub_sub.py —— 靠「字幕位置固定」而不是靠检测框（检测框会漏会歪）：

步骤做法为什么
① 定位硬字幕含描边落在 y 866–982，横跨整幅宽、居中位置固定 → 不需要逐帧检测
② 检测带 ≠ 掩蔽带检测 (866,986) 只算列密度；掩蔽 (850,1010)混用会导致掩码碎成条状
③ 判据带内「列密度 > 0.60 的列数」≥ 15真字幕列数 16–53，其余帧 ≤13
④ 填充整幅宽掩蔽 + 竖向线性渐变填充取带外上下各 6 px 邻带均值插值，不留黑块
阈值踩坑记录（别再调回去）
  • 0.040 → 误判 93.8% 的帧，整带糊掉；0.40 → 误判 9 帧；0.60 + 窄带 → 只剩 6 帧，全为真
  • 行带太窄（880–986）→ 切掉字幕头部 14 px，残字被 inpaint 边界带成黄色横条
  • 行带太宽（856–1005）→ 字幕只占带高 2/3，列密度 0.9→0.4，与背景列混 → 掩码碎成条状
  • stroke_mask + inpaint → 描边本身就是黑的，从边界取色 → 填成黑块

S3–S4 · 音频与提示词

音频两条路，优先原声直切：

  • 原声直切（现行全量线用）：直接取原片该镜的音轨切片 → 音色、环境音、口型天然对。 判别：测 wav 首 0.6 s 均值 —— −7 dB 级 = 原声直切（实测 dy_full_a/*.wav 为 −7.3 dB）。
  • TTS 干声（tts_batch.py，阿里云百炼 sambert）：atempo 调速 → adelay 600 ms → apad 补齐。 判别：−91 dB 级才是 TTS 的静音头。

提示词四条硬标准（audit_content.py 可扫，但扫描只查"有没有写"，好坏必须目视）：

#标准具体判据
S1零字幕无 <d> 标签 + 尾部有 strict_output_constraints 段 + 文字道具带 illegible
S2表情微表情 ≥3、情绪过渡 ≥1、无任何"完全静态"类词
S3位置逻辑多人镜每段有 left/right of frame、foreground 锚点；单人镜有朝向锚点
S4技术对齐时间轴末段结束时间 == scene_duration_seconds
S1 的机理（理解了才不会反复踩）

<d>[Chinese]"…"</d> 会同时驱动口型与屏幕字幕， 尾部写 no subtitles 压不住 —— 必须彻底剥离，比只去引号保险。 另外：干声定口型，面部神态全由 prompt 文字定（写满 unnervingly calm = 木头人）。

不油腻写法（正反两面都要写，缺一面就会出塑料感）：

# 正向
matte finish + visible pores + neutral white balance + muted naturalistic colour
# 负向
no oily sheen / no glossy specular highlights / no beauty-filter / no plastic or waxy skin /
no HDR glow / no over-sharpening / no orange or teal cast

S6 · 队列与门禁：worker 怎么领活

现行主力是目录扫描式 worker（pipeline_worker.sh），核心是三个标记文件构成的门禁：

gates/<k>.done已完成 → 永久跳过。断点续跑就靠它
gates/<k>.lockmkdir 原子锁 → 防两卡抢同一镜
gates/<k>.fail失败过 → 不再自动重试（删掉才重跑）
WF_DIR / GATE_DIR环境变量切产线，gates 必须独立
# 单卡（现行）：一个 worker，不切分 keys
cd /workspace/dy_key && setsid nohup bash run_dy_single.sh full \
  > run_full.log 2>&1 < /dev/null &

# 双卡：两卡各一个 worker，抢 wf/ 下未完成的镜
WF_DIR=$PWD/wf_full GATE_DIR=$PWD/gates_full bash pipeline_worker.sh A 8188 &
WF_DIR=$PWD/wf_full GATE_DIR=$PWD/gates_full bash pipeline_worker.sh B 8189 &

每轮循环做四件事：扫 wf_*.json → 跳过已 .done 的 → mkdir 抢锁 → 调 submit_api.py 提交并轮询到结束 → 打 .done、删锁。

为什么是"目录扫描"而不是"任务列表"：可以边生成边投喂——本机写完一镜 prompt 就 scp 过去， worker 下一轮自动领走，GPU 不空转。

S7 · 回收：跨境链路是另一个瓶颈

★ 回传慢不是带宽问题，是丢包

症状：ssh 敲命令飞快，但 scp 只有 0.1 MB/s。 真因是泰国→中国跨境段丢包：ss -tni 里 cwnd:2 ssthresh:2 retrans:7835， cubic 反复 RTO 把窗口压回 2 个 MSS，单流只剩 ~150 Kbps。 服务器自己下外网实测 26.5 MB/s，说明链路没问题。

一次性修复：开 BBR + 16 MB 收发缓冲（已持久化到 /etc/sysctl.d/99-net-speed.conf）→ 0.11 → 6 MB/s（约 50 倍）。 判据：cwnd 个位数 + retrans 上千 = 丢包型限速，开 BBR； cwnd 很大但仍慢 = 真带宽上限，只能压文件。

# 服务器端先压预览，只把终稿拉全质量
ssh kehu 'cd <输出目录> && for f in *.mp4; do b=${f%_00001_.mp4}; \
  ffmpeg -y -loglevel error -i "$f" -vf scale=384:-2 -c:v libx264 -crf 30 \
    -preset veryfast -c:a aac -b:a 48k -movflags +faststart /tmp/prev_${b}.mp4; \
  ffmpeg -y -loglevel error -i "$f" -vf "fps=1/2,scale=640:-2" -q:v 3 /tmp/hi_${b}_%02d.jpg; done'
scp -q "kehu:/tmp/prev_*.mp4" out/preview/
scp -q "kehu:/tmp/hi_*.jpg"   out/stills/

3 镜只有约 2.3 MB，几十秒拿完。

三、单镜内部：558 秒花在哪

先给结论：一镜的耗时 ≈ 4 步采样的线性累加 + 固定的解码/封装开销，而每步的开销随帧数平方增长。

冷启首镜820 s比热态多 253 s · 每实例只付一次
热态单镜561 sn=33 · 区间 541–578 s 极稳
354 帧每步119.4 s其中注意力占 62%
107 帧每步18.4 s帧数砍 1/3，步耗降 6.5 倍

三点拟合：帧数 → 秒数（可直接当函数用）

cost = lambda frames: 0.812*frames + 0.002129*frames**2 - 1.3

★ 二次项从哪来 —— 这就是加速的天花板所在

拟合式 step = 0.128·N + 5.96e-4·N²。一次项是 O(N) 的卷积/归一化/GEMM， 二次项是 O(N²) 的注意力。354 帧时二次项占每步 62%、占全流程约 54% （全流程另有 ~69 s 的 VAE 解码/封装等线性开销）。

对账方法（可复现）

四、加速 · L0 零成本层

这一层不动任何一个算子、不装任何东西，纯靠调度和参数选择。收益比 L2 大，风险为零， 所以永远先做这一层。

#动作收益依据
1 按原片真实镜长定 length，不要一律拉满 354 帧 10.6× 373 镜实测：帧数中位 56、均值 65、区间 22–345。按镜长切 → GPU 机时 5.4 h； 一律 354 帧 → 30 h。成片 276–292 s 与原片 288–297 s 几乎重合
2 保持 4 步（全量线），6/8/12 步不是杠杆 省 1.5–3× 采样时间 同镜同 seed 跑 4/6/8/12 步，SSIM vs 钉死首末帧： 4步 0.850/0.629 · 6步 0.659/0.671 · 8步 0.666/0.712 · 12步 0.651/0.657 —— 非单调（混沌）。目视：6/12 步连起点都没守住，8 步两端打架。 步数省下的时间换多个 seed 备选更划算
3 热态连续跑，中途不 /free 卸权重 −20%/镜 A100 冷启 = 热态 4–5×（382 → 74 s）。每镜多卸一次权重 = 每镜多付 ~96.8 s 冷加载。 ⚠ 旧文档里「每镜前释放显存」的说法与本铁律直接冲突，照抄会白烧 20% 机时
4 冷启只算一次，绝不乘镜数 记账纠错 冷启 820 s 只在批次第一镜付，全项目最大的记账陷阱
5 多卡 = 吞吐翻倍，不是单镜提速 别走弯路 一镜拆不到两卡。N 镜分布 ⌈N/2⌉+⌊N/2⌋，挂钟由跑得多的那张卡决定， 另一张提前空闲属正常。单任务双卡 SP=2 反而更慢（见 L3）

L0 的实际战绩

手段否决理由
SageAttention 全局开关 --use-sage-attention 本机实测 791 s 且输出全 NaN。
根因：H3 内核硬依赖 _sageattn_int8_fp8_nhd，SM80 无原生 FP8。必须走 KJ patch 路线（L2 #3）
VSA-H3 稀疏注意力（0.9） 原生核只编 sm_100a/sm_103a（Blackwell）； 且官方模型卡原话「FL2VA and Ref2VA were not distilled」—— 你的用例（Ref2VA）根本没被蒸馏过
T8 节点包的 SLA 后端 h3_t8/sla_attention_advanced.py 源码里硬钉 capability == (8,9)， 非 sm89 直接 raise；且有盲评硬失败记录
chunk-star7 SLA（Triton 路径） 本环境 triton: available=True 但 disabled=True → 路径当前不可用；SM80 实测数字缺失
Progressive attention 官方 −37%，但明写不支持多参考/尾帧 —— 正是 Ref2VA + first/last frame 的用法
FlashAttention 4 需 sm90+，A100 自动落回 FA2
FP8 / NVFP4 权重 FP8 matmul 需 sm89+，低于此自动回退 bf16 反量化 → 无收益（FastVideo 文档原文）
TeaCache 已装但禁用。4 步下缓存过狠 → 尾段拖影/涂抹。 实测去 TeaCache 后热态 531–551 s，与带 TeaCache 基本持平 —— 在 4 步下毫无提速价值。 不要再往 wf_one/wf_full 里加 TeaCache 节点
多卡单任务（SP=2 / tensor parallel） 唯一可引用的 H3 多卡数据是 1.2–1.35×（GB10 配对，21 GB/s RoCE）。 按 1.3× 推算：469 ÷ 1.3 ≈ 361 s/镜 × 24 镜 ≈ 2.4 h， 比双实例 1.56 h 更慢。要打平双实例需 >2× 加速，SM80 PCIe 拓扑下不可能。 且 A100-PCIE 无 NVLink，P2P 走 PCIe，NCCL 表现可能更差

8.2 整批挂钟

形态公式373 镜代入
单卡 挂钟(h) ≈ Σcost(frames) / 3600 + 冷启溢价 6.57 h → 6h34m
双卡 挂钟(h) ≈ 镜数 / 12.25 + 0.07 ≈3.37 h（按镜切）；按台词句切 ≈3.3 h
★★ 单卡换算律（最好记的一条）

双卡报告里的「GPU 总机时」= 单卡下的「挂钟」。 因为加速比 1.950× 的必然结果 —— 两卡合计的机时被摊到两条并行线上。 单卡挂钟 ≈ 双卡 × 2。实测依据：33 镜总机时 18908 s = 5h15m（双卡挂钟 2h35m）。

一句话说清单卡的影响：单卡只影响排队长度，不影响单镜速度 —— 每一镜本身的 561 s 与卡数无关，373 镜从 3.37 h 变成 6h34m 而已。

★ 排期别只算 GPU

实测一次端到端 5h59m 里，人工目视审查占了 3h06m = 52% （关键镜 + 产品镜多轮 v1/v2/v3），GPU 生产只占 45%。 给用户的工期要按 2 倍 GPU 时间报。

九、会静默毁结果的坑

这些坑的共同点是：不报错。要么静默跳过，要么误导你去查错方向。

症状真因处置
所有检查都报「ComfyUI 没响应」，但端口确实在监听 环境里有 http_proxy（WorkBuddy / Clash 都会设）， curl 127.0.0.1:8188 走了代理拿 502 export no_proxy="127.0.0.1,localhost,::1"（NO_PROXY 一起设）。 自查：返回 502/000 但 ss -ltn 有监听 = 就是这个。 ★ 但下载权重的脚本不能加这个
某镜既不跑也不报错（静默缺席） gates/ 里残留的 .lock 空目录 （worker 被 kill / 机器关机留下）—— worker 见 lock 即 skip find gates* -maxdepth 1 -type d -name '*.lock' -exec rmdir {} \;
★ 实机确认：gates_full/dy1_s009.lock、dy1_s010.lock 仍在
某镜反复失败、机时白烧 原版 pipeline_worker.sh 失败后释放 lock，下一轮又领到同一镜 → 死循环 归档版已加 <k>.fail 标记（失败即跳过，删掉才重跑）。 单卡长跑必查 —— 双卡时另一张卡在出片，不容易察觉
显存高但在空转 / 内存爆 ComfyUI 跑完不自动释放；空闲实例常驻 ~57 GB 内存 显存高 ≠ 在忙，以 /queue 为准。点火前必查队列并主动 /free。 POST /free 返 200 但响应体 0 字节，别对它 json.loads()
ssh 一断任务就没了 后台进程挂在 ssh 会话上 setsid nohup … > log 2>&1 < /dev/null & —— 少一个 stdin 重定向都会被带走
清队列把自己 ssh 掐断 pkill -f "ComfyUI/main.py" 会匹配到执行它的那条 ssh 命令行 → 自杀式断连 清队列用 POST /queue {"clear":true} + POST /interrupt； 杀进程用 ps -eo pid,args | grep "[x]xx" 定位 PID
第二实例起来就锁死（仅双卡） 两实例共用 ComfyUI/user/*.db → Database is locked 8189 必须带 --database-url sqlite:////workspace/instance_b.db（四个斜杠）。 ★ 单卡单实例天然免疫，也不要建这个库
后台脚本跑在原 cwd shell 优先级：cd X && A & B & 里 B 跑在原 cwd 后台提交一律用绝对路径

十一、一页总结

流程

拆解 → 按台词句切单元 → 备零文字参考帧 + 原声 → 写四条硬标准的 prompt → 装配 16/18 节点工作流 → worker 扫描队列提交 → ComfyUI 4 步采样出片 → 压预览回传目视。

加速（按该做的顺序）
  1. L0 先做：按真实镜长定帧数（10.6×）、保持 4 步、热态连续跑不卸权重（−20%）、冷启只算一次
  2. L1 已吃满：v0.36.0 算子融合（−20.5%）+ ck-attention + Turbo 4 步 + int8_convrot
  3. L2 下一步：先做半天零风险的算子 profile；然后 INT8 ConvRot VAE（稳，−3~4%）； 再赌 Sage+KJ patch（唯一有机会再拿 −20%，但必须重过质检）
  4. L3 别再试：VSA / T8-SLA / Progressive / FP8 / FA4 / TeaCache / 多卡单任务 / torch.compile / TRT VAE
加速天花板一句话

注意力在 354 帧时占每步 62%，这就是所有 attention 类加速的上限； A100 无 FP8 → k 现实值 1.3–1.8 → 全流程还能省的只有 −12%~−20%。 想再往下，只能改帧数或切分单位，那是 L0 的地盘 —— 而 L0 已经拿走了 10 倍。
