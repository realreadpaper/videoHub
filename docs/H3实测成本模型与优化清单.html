MiniMax-H3 产线实测成本模型与优化清单

停机前最后一次全量回传数据的实测结论 —— 一个 124 帧「地板」吃掉了近一半算力
分析日期：2026-09-19 数据来源：kehu 2×A100-PCIE-40G（华为云泰国） 依据：2794 个回传文件 · 36 个 worker 日志 · 145 条逐镜计时 · 节点源码
一句话结论

现行工作流有一个硬编码的 124 帧（5.167 s）渲染地板：任何短于它的镜头都会被补齐到 124 帧再渲染，成片裁回请求长度。 373 镜全量线里有 348 镜（93.3 %）落在地板以下，导致付费帧数是实际需要帧数的 1.94 倍。 因此 373 镜的真实 GPU 机时是 ≈14 h（双卡挂钟 ≈7 h / 单卡 ≈14 h）， 而不是部署手册里写的 6.57 h —— 低估约 2.1 倍。

一、124 帧地板：机制与证据

工作流里的音频窗口节点 MiniMaxH3AudioWindowT8 带一个参数 ensure_minimum_context（本工程全部批次均为 true）。 它在 custom_nodes/comfyui-minimax-h3-audio-T8/h3_t8/timing.py 里的实现只有三行关键代码：

required = warmup_seconds + scene_duration_seconds + cooldown_seconds
if ensure_minimum_context:
    required = max(required, MIN_TRAINED_FRAMES / FPS)   # MIN_TRAINED_FRAMES = 124, FPS = 24

也就是说：请求时长被抬到 124 帧（= 5.167 s）之后才送去采样，渲染完再由下游的 MiniMaxH3OutputTrimT8 裁回用户请求的长度。多渲的那部分算力直接丢掉。

常量（h3_t8/core.py）值含义
FPS24帧率
MIN_TRAINED_FRAMES124地板 —— 低于此长度按此长度渲染
MAX_TRAINED_FRAMES362上限
帧栅格 align_frame_count()17n + 5向上对齐（124 = 17×7+5，362 = 17×21+5）

直接证据：帧数变 4 倍，耗时一动不动

dy_full 批次的 12 个镜，请求帧数从 22 到 90 横跨 4 倍，实测耗时却全部是 110.1 s：

三、三条成本曲线的实测斜率

3.1 帧数 —— 地板以下是平的

请求帧实渲帧实测每镜秒单价

纠正旧结论 「短镜每秒更便宜」在现行产线上不成立

因为有地板，39 帧的短镜每镜秒要付 67.7 s，而 345 帧的长镜只要 38.5 s —— 长镜反而更划算。切短不会省时间，切到 124 帧以下再切多短都是同一个价。

3.2 参考图数量 —— 每多一张约 +20 s

1 张110.1 s—wf_full 全量线

这组对比同时解释了一个此前的疑点：为什么同样「被补齐到 124 帧」，各批次耗时却是 110 / 130 / 145 三档 —— 差异来自参考图数量，不是帧数。全量线固定用 1 张，已经是最省的选择。

最小二乘：T ≈ 55 + 21.3 × steps（124 帧 / 2 张参考图基准）。四个点几乎完美落在一条直线上。

结论不变，理由要改 「保持 4 步」依然正确，但原因不是「加步数不涨时间」

此前「4/6/8/12 步耗时非单调」的印象，是排队等待污染出来的假象（12 步其实单调递增）。 正确的说法是：每加一步线性多花 21.3 s，而质量在 4 步之后不再提升（SSIM 非单调） —— 所以 4 步是「性价比拐点」，不是「免费午餐」。

5.2 「用时」含排队，不是纯 GPU 时间

worker 日志打的 [✓] 用时 XXX s 是提交 → 完成的挂钟时间，包含在 ComfyUI 队列里等待的时间。 直接证据来自 dy_key/S6.log（每 10 s 记录一次 排队 / 运行）：

  0 s – 220 s    排队 1 / 运行 1    ← 我们的任务还没被调度，在别人占用的实例上排队
230 s – 370 s    排队 0 / 运行 1    ← 真正在跑
380 s – 400 s    排队 1 / 运行 1    ← 新任务入队

=> 用时 410.5 s 中约 230 s 是排队，纯执行只有约 180 s
会毁掉加速结论 拿日志里的「用时」横向比不同步数 / 不同批次，会把「排队久」误读成「这一步慢」

建议 worker 拆成两个计时：submit → start（排队）与 start → done（执行）， 分别落盘。这是本案唯一「不花钱就能让后续实验可信」的改动。

六、优化清单

按「省得多 / 风险低」排序：

#动作预期收益风险
O1 切分时把单元时长往 5.17 s 靠。既然 124 帧以下同价，就没有任何理由切得更短 —— 把相邻短句合并到接近 124 帧，等于免费换来更长的镜头，同时减少镜数（连带减少人工目视成本） 镜数下降，单镜成本不变 低
需守住「1.6 s 金句短单元不可合并」这条铁律
O2 保持 1 张参考图，不要随手加到 2–3 张 相对 3 张省 31 % 低
O3 保持 4 步 每加 1 步 +21.3 s / 镜 低
O4 修正排期口径：373 镜按双卡 ≈7 h / 单卡 ≈14 h 报 避免排期与成本错判 零
O5 接手前清 .lock，并核对「提交数 = .done + .fail」 防静默丢镜 零
O6 worker 拆分计时：排队 / 执行分开落盘 让后续加速实验可信 零
O7 查 MIN_TRAINED_FRAMES 是否可配：若模型支持更小的地板，短单元的成本会直接下降 潜在最大（矩阵成本） 中
必须试拍验证画质是否崩
O8 复现 dy1_s003/s004/s009/s010 的确定性失败 消除 4.1 % 失败率 低
已实测否决、不要再试的三件事
  • ✗ 「切更短可以更快」 —— 地板之下全是同一个价；短镜每镜秒反而更贵（67.7 s vs 38.5 s）。
  • ✗ 用 worker 日志的「用时」横向比较不同配置 —— 被排队等待污染。
  • ✗ 按请求帧数估算总机时 —— 漏掉 1.94 倍的补齐开销，会低估 2.1 倍。
