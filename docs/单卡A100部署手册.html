1 · 单卡形态是什么

一句话

单卡只影响「排队长度」，不影响「单镜速度」。
每一镜本身的 9 分 18 秒（558 s）由模型和分辨率决定，跟你有几张卡毫无关系—— 你要丢 373 镜进去，双卡 3.4 小时出完，单卡 6.6 小时出完，仅此而已。

具体的形态差异是：单卡只有一个 ComfyUI 实例（8188），只跑一个 worker。 双卡那套「两个实例 + 两个 worker 抢镜」的设计，在单卡上不但没有收益， 还会因为两个实例同时抢内存而 OOM。

⚠ 反过来也成立：单卡脚本别在双卡机器上跑

04_launch_comfy.sh single 只会启动 GPU0 上的 8188。 在双卡机器上这么干，GPU1 全程闲置——你照样付两张卡的钱。 双卡机器用 both + 两个 worker。

3 · 目标机硬要求 + 内存这个坑

项要求说明
GPU1× A100-PCIE-40GB
（SXM4-40GB 也可以）		都是 SM80，兼容性完全一致；SXM4 略快一点
显存40 GB基准就是 40 GB，别选更小的
内存≥ 96 GB（推荐 128 GB）★ 最容易踩的坑，见下
磁盘≥ 150 GB权重 71 GB + ComfyUI/venv 8 GB + 长跑输出
驱动≥ 580（基准 580.95.05）torch cu130 自带 CUDA 13 运行时，系统不用装 CUDA Toolkit
OSUbuntu 22.04脚本按 apt 写
网络能直连 HuggingFaceModelScope 在境外机房等于不通
★ 为什么单卡也必须给到 96 GB 内存 —— 别顺手选小内存机型

一根 40 GB 的卡装不下 50.2 GB 权重，必然要把一部分放在内存里换进换出。 旧机实测：单个空闲的 ComfyUI 进程就常驻 57 GB 内存（双卡就是 2×57 GB， 125 GB 的机器只剩 1.1 GB free）。

所以租卡时选个 64 GB 内存的机型，跑到一半就会 OOM。 这是本项目最贵的一类失误——跑到第 200 镜崩掉，前面烧掉的机时无法找回 （gates 只能保住进度，保不住钱）。
00_check_target.sh 已内置这条判定：内存 < 96 GB 直接报 [FAIL]。

swap 不能解决这个问题

01_provision_os.sh 会建 8 GB swap，但它的定位是 安全气囊，不是内存扩展。真开始用 swap 时，云盘 IO 抖动会表现为「整机卡死」， 比 OOM 还难排查。别指望 8 GB swap 兜住 32 GB 的缺口。

4 · 部署：照旧走 bootstrap，只有 4 处不同

下面 5 行命令与双卡一字不差，照跑即可（00 会自动判定为【单卡模式】）：

# 新机上 —— 与双卡完全相同的流程
bash deploy/bootstrap/00_check_target.sh     # 体检：会判定【单卡模式】+ 校验 96 GB 内存线
bash deploy/bootstrap/01_provision_os.sh     # apt / 8 GB swap / BBR
bash deploy/bootstrap/02_build_stack.sh      # venv + torch + ComfyUI v0.36.0 + 3 个节点
bash deploy/bootstrap/03_dl_weights.sh       # 71 GB 权重（最慢一步，挂着睡一觉）
bash deploy/bootstrap/04_launch_comfy.sh single   # ★ 差异 1

# 本机（macOS）—— 推资产，05 会连单卡脚本一起推过去
bash deploy/bootstrap/05_push_assets.sh <新机别名>

# 目标机 —— 真出一镜验证链路
bash deploy/bootstrap/verify.sh --run

差异 2 · 不要建 instance_b.db

单卡只有一个 ComfyUI 进程，不需要第二个数据库。建了纯属占盘，还会误导后来的人以为这是双卡环境。

差异 3 · 整盘 rsync 搬过来的话，清掉双卡残留

# 旧机双卡时代留下的锁 —— 会让单实例起不来或行为异常
rm -f /workspace/instance_b.db /workspace/instance_b.db.lock
rm -f /workspace/ComfyUI/user/comfyui.db.lock

# ★ venv 里写死了旧机的绝对路径，跨机搬过来基本是坏的 —— 别偷懒
mv /workspace/venv /workspace/venv.broken && bash deploy/bootstrap/02_build_stack.sh

差异 4 · 跑批前做一次「接手检查」

旧机的门禁目录里会留有三类脏状态，它们全都不报错，只会静默跳过或死循环。 见 §8。

5 · 启动（single）

bash deploy/bootstrap/04_launch_comfy.sh single    # GPU0 → 8188
bash deploy/bootstrap/04_launch_comfy.sh status    # 存活实例数 + 队列 + 显存
bash deploy/bootstrap/04_launch_comfy.sh stop      # 停（按 /proc 精确匹配，不会自杀式断连）

它等价于这条手写命令：

CUDA_VISIBLE_DEVICES=0 setsid nohup /workspace/venv/bin/python /workspace/ComfyUI/main.py \
  --listen 127.0.0.1 --port 8188 --vram-headroom 1 --use-ck-attention \
  > /workspace/logs/comfy_single.log 2>&1 < /dev/null &
参数作用单卡要注意什么
--use-ck-attention走 comfy-kitchen 的 INT8 注意力通路与卡数无关，必须带。A100（SM80）上唯一有效的注意力加速
--vram-headroom 1DynamicVRAM 额外留 1 GB保持默认，别调
--database-url sqlite:///…给实例 B 用独立数据库单卡不需要，整条参数删掉
setsid … < /dev/null &脱离 ssh 会话三个都不能少，否则 ssh 一断任务就被带走
不用 --listen 0.0.0.0

监听 127.0.0.1 就够了（提交器跑在同一台机器上）。 暴露到公网既无必要也不安全。

6 · 跑批：单 worker，不切分 keys

双卡要按 keys 对半分给两个 worker。单卡一个 worker 就够—— pipeline_worker.sh 的目录扫描 + 原子锁 + gates 断点续跑， 本来就是为「不确定跑多久」设计的，单卡下就是最优解，不需要手工分片。

两个 run_*_single.sh 由 05_push_assets.sh 自动推到目标机， 不依赖任何双卡脚本，可以独立使用。

长批次建议：按片分批，顺便中途审片

373 镜要跑 6.6 小时，中断风险不小。 pipeline_worker.sh 按 wf_*.json 的字典序扫描， 所以是按片顺序跑的（报恩 99 → 继母 119 → 挑食 155）。你可以在任意时刻 kill 掉 worker，gates 会记住进度，下次 run_dy_single.sh full 自动从断点续。这就允许「跑到第 99 镜停下来审片，确认方向后再继续」。

7 · 时间账怎么算

核心换算式（好记）

双卡报告里的「GPU 总机时」= 单卡下的「挂钟」。
原因很直观：双卡就是把「所有镜的总耗时」摊到两条并行的线上。 旧机实测加速比 1.950×（理论 2.0，损耗来自两卡镜数不均衡 + 各付一次冷启）。

实测数据（旧机，v0.36.0 + Turbo 4 步 + ck-attention）

产线镜数GPU 总机时双卡挂钟单卡挂钟
抖音关键镜（实跑完）33 18908 s = 5h15m2h35m 5h15m
抖音全量复刻373 6.57 h3.37 h 6h34m
三部曲24 未整批实测≈1.9 h ≈3h45m（外推）

单镜耗时口径

口径数值说明
热态（排期用这个）558 sn=31 实测，区间 541–578 s，非常稳
首镜冷启820 s比热态多付 ~262 s，一个批次只付一次
每镜都冷启（反事实上界）~2400 s不要用于排期

于是：单卡挂钟 ≈ 镜数 × 558 s + 262 s

两个容易算错的地方
  • 373 镜不能按 558 s 乘。那 6.57 h 对应的是平均 63 s/镜—— 因为全量复刻的镜长是原片长度（22–175 帧，均值 90），而 558 s 是 354 帧满长镜的口径。 帧数差 4 倍，注意力是 O(N²)，耗时自然差得多。
  • 冷启在长批次里可以忽略，在试拍里就是全部。 373 镜 6h34m 里冷启只占 0.7%；但试拍 1 镜时，冷启就是 100% 的成本。 别用单镜试拍的时间去估批量。

三部曲那个 ≈3h45m 的来历，说清楚

它是外推值，不是实测。口径取 ref2va 主干的热态 558 s/镜： 24 × 558 + 262 ≈ 13654 s ≈ 3h47m。
如果你那批用的是更快的 fl2va 主干（v0.36 实测端到端 469.3 s）， 则是 24 × 469 + 262 ≈ 11518 s ≈ 3h12m。所以区间是 3h10m–3h50m， 取决于该批走哪套权重。双卡手册里写的「24 镜 ≈1.5 h」是双卡口径，别拿来比。

8 · 接手检查清单（必做）

门禁目录里的三类脏状态 —— 全都不报错，只会静默跳过或死循环

这是本项目最阴的一类故障：进度条在走，但某些镜就是不出片， 而且没有任何错误信息指向它。

cd /workspace/dy_key

# ① 残留 .lock —— 双卡 worker 被 kill / 机器关机留下的空目录
#    后果：该镜被【永久跳过】，既不跑也不报错
find gates gates_full -maxdepth 1 -type d -name '*.lock'
find gates gates_full -maxdepth 1 -type d -name '*.lock' -exec rmdir {} \;

# ② 残留 .fail —— 此前失败的镜
#    后果：被跳过。确认修好了再删，删掉即重跑
ls gates*/*.fail
# rm gates/*.fail gates_full/*.fail

# ③ 旧实例的数据库锁 —— 整盘 rsync 搬过来的机器
rm -f /workspace/ComfyUI/user/comfyui.db.lock /workspace/instance_b.db.lock

run_dy_single.sh 已内置 ① 和 ③ 的自动清理， 而且会在检测到已有 worker 在跑时拒绝启动（否则清 lock 会破坏互斥）。

另一个真 bug 已修（2026-09-19）：失败镜无限重试

原版 pipeline_worker.sh 在 FAIL 之后只写 failed_*.txt 并释放 lock，下一轮扫描又领到同一个镜 → 死循环烧机时。 双卡时另一张卡还在出别的片，不容易察觉；单卡跑 373 镜时会直接卡死在那里。
归档版已加 .fail 标记：失败即跳过、不再自动重试，删掉标记才重跑。
★ 旧服务器上跑的还是老版本 —— 用 deploy/server-assets/dy_key/pipeline_worker.sh 覆盖过去（05_push_assets.sh 推的就是修好的版本）。

9 · 单卡坑位清单（8 条专属 + 2 条通用必读）

#坑后果 / 正确做法
1选 64 GB 内存的机型 单张 40 GB 卡装不下 50.2 GB 权重，必然 offload 到内存；单个空闲实例就吃 57 GB。 跑一半 OOM。门槛 ≥ 96 GB
2在双卡机上跑单卡脚本 只启 GPU0，GPU1 白付租金。双卡机器用 both + 双 worker
3在单卡机上起两个实例 两个进程抢内存 → OOM。单卡只起 8188
4照抄双卡的 --database-url 单实例不需要，还会让人以为要建 instance_b.db。整条删掉
5残留 .lock 目录 该镜被永久跳过且不报错。接手前清一遍，见 §8
6失败镜无限重试（原版 worker） 死循环烧机时，单卡长跑必现。用归档版（带 .fail 标记）
7按 558 s/镜去估 373 镜 会算出 57 小时。373 镜平均只有 63 s/镜（帧数少 4 倍）。直接用总机时 6.57 h
8把冷启时间乘镜数 冷启只在批次第一镜付一次。373 镜里占 0.7%，试拍 1 镜里占 100%
9环境里有 http_proxy（通用坑，但单卡最常撞） WorkBuddy / Clash / 公司代理都会设。此时 curl 127.0.0.1:8188 会走代理拿到 502，所有检查脚本都报「ComfyUI 没响应」——而它其实跑得好好的。 你会白翻半天日志、反复重启实例。解法：脚本开头 export no_proxy="127.0.0.1,localhost,::1" （NO_PROXY 一起设）。本手册配套的脚本已全部内置。
10变量后紧跟中文标点（改脚本时容易引入） set -u 下 echo "端口 $PORT）" 会报 unbound variable（bash 把全角括号的字节当成变量名一部分）； 没开 set -u 则静默展开成空串。变量一律写 ${VAR} 形式。

通用坑位（17 条：commit 版本、TeaCache、pkill 自杀式断连、 /free 空响应体、BBR、权重子目录…）见 docs/新服务器部署手册.html §10 与 deploy/README.md §4 —— 那些与卡数无关，单卡同样适用，务必一并读。

10 · 验收

bash deploy/bootstrap/verify.sh        # 静态检查
bash deploy/bootstrap/verify.sh --run  # 真出一镜（约 10 分钟，含冷启）
单卡验收时，除了通用检查项，额外确认这三条：
  • 存活实例数 = 1（04_launch_comfy.sh status 会打印）；8189「未启动」是正常的，不是故障
  • nvidia-smi 只有一张卡，memory.used 在跑任务后应接近 40 GB（说明权重已驻留）
  • free -g 的 available 应还剩 ≥ 25 GB；如果只剩个位数，说明这台机器内存给少了

出片后的产品侧验收（不烧字幕、字幕绝对时间 = Σ前序镜时长、 length 只接受 17n+5、一步直出成片时长 = H3 帧数 ÷ 24） 见主手册 §12，与卡数无关。
