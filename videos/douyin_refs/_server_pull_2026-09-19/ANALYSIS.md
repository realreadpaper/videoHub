## 一、最重要的一条：124 帧「补齐地板」

### 事实

工作流节点 `MiniMaxH3AudioWindowT8` 带参数 `ensure_minimum_context: true`。
它的实现在 `custom_nodes/comfyui-minimax-h3-audio-T8/h3_t8/timing.py`：

```python
required = warmup_seconds + scene_duration_seconds + cooldown_seconds
if ensure_minimum_context:
    required = max(required, MIN_TRAINED_FRAMES / FPS)   # MIN_TRAINED_FRAMES = 124, FPS = 24
```

即：**任何短于 124 帧（5.167 s）的镜头，都会被补齐到 124 帧去渲染，渲染完再由
`MiniMaxH3OutputTrimT8` 裁回请求时长。多渲染的部分直接丢掉。**

相关常量（`h3_t8/core.py`）：

| 常量 | 值 | 含义 |
|---|---|---|
| `FPS` | 24 | 帧率 |
| `MIN_TRAINED_FRAMES` | **124** | 地板：低于此长度按此长度渲染 |
| `MAX_TRAINED_FRAMES` | **362** | 上限 |
| 帧栅格 | **17n + 5** | `align_frame_count()` 向上对齐 |

### 对 373 镜全量线的实际影响

```
请求帧数: 中位  56   均值  65.3   合计 24373
实渲帧数: 中位 124   均值 126.6   合计 47204
```

| 指标 | 数值 |
|---|---|
| 请求 < 124 帧（被补齐）的镜 | **348 / 373 = 93.3 %** |
| 实渲帧数分布 | 124 帧 × **348**；141×14；158×6；192×3；209×1；345×1 |
| 付费帧数 ÷ 请求帧数 | **1.94 ×** |

用工程既有标定公式 `f(N) = 0.812N + 0.002129N² − 1.3`（4 步 / 1 张参考图 / 整镜总时长）：

| 口径 | 373 镜总 GPU 机时 | 双卡挂钟 | 单卡挂钟 |
|---|---|---|---|
| 按**请求帧数**（旧口径） | 23646 s = **6.57 h** | 3.4 h | 6h34m |
| 按**实渲帧数**（真实） | 50730 s = **14.09 h** | **7.0 h** | **14.1 h** |
| 虚增 | **× 2.15** | | |

> ⚠ **部署手册里「373 镜 双卡 3.37 h / 单卡 6h34m」低估了约 2.1 倍**，因为没算补齐。
> 排期、成本报价、单卡机型选择都要按 **14 h 量级**重算。

### 实机交叉验证

同一工作流（39 帧请求 → 124 帧实渲）跑不同批次，实测耗时**完全相同**：

| 批次 | 请求帧 | 实渲帧 | 实测 |
|---|---|---|---|
| `dy_full`（12 镜，帧数 22 / 39 / 56 / 90 混杂） | 22–90 | 124 | **全部 110.1 s** |

帧数从 22 变到 90（4 倍），耗时一动不动 —— 这就是地板的直接证据。

## 二、三条成本曲线的实测斜率（同族工作流对比）

### 2.1 帧数：地板以下免费，地板以上近似线性

| 请求帧 | 实渲帧 | 实测 | 备注 |
|---|---|---|---|
| 22 / 39 / 56 / 90 | 124 | 110.1 s | 地板内，全等价 |
| 354（骨架镜） | 362 | 545–578 s | 中位 560.6 s，n=33 |
| 354 首镜 `dy1_s02_takein` | 362 | 819–820 s | 冷启异常值（热态 4–5 倍记账陷阱） |

**结论：cut 到 124 帧以下不省时间。**「短镜每秒更便宜」在现行产线上**不成立** ——
按每镜秒单价算：39 帧（1.625 s 成片）花 110 s = **67.7 s/镜秒**；
345 帧（14.4 s 成片）花 555 s = **38.5 s/镜秒**。**长镜更划算。**

### 2.2 参考图数量：每多一张 ≈ +20 s

| 参考图 | 实测（124 帧 / 4 步） | 用到它的批次 |
|---|---|---|
| 1 张 | **110.1 s** | `wf_full` 全量线 |
| 2 张 | **130.2 s** | `wf_v3full` / `wf_pv2` / `wf_pv3` / `wf_v2B` / `wf_v2C` |
| 3 张 | **145.0 s** | `wf_six` / `wf_six2` / `wf_six3` / `wf_Dtest` |

全量线固定 1 张参考图 → 已是最省的选择。若要加 Hybrid 多图，按 +18%／+32% 计价。

### 2.3 步数：严格线性，21.3 s/步

同族工作流（39 帧请求 → 124 帧实渲）实测：

| 步数 | 实测 | 说明 |
|---|---|---|
| 4 | 140.1 s | |
| 6 | 180.0 s | **日志记的是 410.5 s，其中 230 s 是排队等待**（见 §4） |
| 8 | 230.3 s | |
| 12 | 310.3 s | |

最小二乘：**T ≈ 55 + 21.3 × steps**（124 帧 / 2 张参考图基准）。

**步数是纯线性杠杆** —— 此前「4/6/8/12 步耗时非单调」的印象是排队污染造成的假象。
质量侧结论不变（SSIM 非单调、4 步已够），但**理由要改**：不是「加步数不涨时间」，
而是「**加步数线性涨时间，且质量不涨**」。

### ⚠ 两个 `.lock` 残留会静默吞镜

```
dy_key/gates_full/dy1_s009.lock
dy_key/gates_full/dy1_s010.lock
```

这两镜此前**生成失败**（见 §4），worker 留下 `.lock` 未清。
按 `pipeline_worker.sh` 的门禁逻辑，**有 `.lock` 的镜会被永久跳过且无任何提示**。
接手前必须先清：

```bash
find gates_full -maxdepth 1 -type d -name '*.lock' -exec rmdir {} \;
```

## 四、失败镜与度量陷阱

### 4.1 失败明细（6 / 145 条计时记录 = 4.1 %）

| 日志 | 镜号 | 耗时 | 失败节点 |
|---|---|---|---|
| `dy_key/FA.log` | `dy1_s010` | 70.1 s | `SamplerCustomAdvanced` (node_id=10) |
| `dy_key/FB.log` | `dy1_s009` | 90.1 s | `SamplerCustomAdvanced` |
| `dy_key/VA.log` | `dy1_s003` | 90.1 s | `SamplerCustomAdvanced` |
| `dy_key/VB.log` | `dy1_s004` | 90.1 s | `SamplerCustomAdvanced` |
| `dy_key/SIXB.log` | `dy2_s118` | 50.1 s | `SamplerCustomAdvanced` |
| `trilogy/test_f1s01.log` | `f1_s01` | 590.7 s | （三部曲试拍） |

失败集中在少数镜号（`dy1_s003/s004/s009/s010`），且全部卡在采样器节点，
高度疑似与特定参考帧 / 音频切片有关的确定性失败，而非随机显存问题 —— 值得单独复现定位。

### 4.2 「用时」含排队，不是纯 GPU 时间

worker 日志打的 `[✓] 用时 XXX s` 是**提交 → 完成**的挂钟，包含在 ComfyUI 队列里等待的时间。

直接证据（`dy_key/S6.log`，每 10 s 打一次 `排队 / 运行`）：

```
0s  – 220s   排队 1 / 运行 1     ← 我们的任务还没被调度，在被别人占用的实例上排队
230s – 370s  排队 0 / 运行 1     ← 真正在跑
380s – 400s  排队 1 / 运行 1     ← 新任务入队
=> 用时 410.5 s 中，约 230 s 是排队，纯执行只有约 180 s
```

**这条陷阱会直接毁掉加速结论**：拿 `用时` 做对比，会把「排队久」误读成「这一步慢」。
建议 worker 拆成两个计时：`submit → start`（排队）与 `start → done`（执行）。

## 五、模型校准核对

`f(N) = 0.812N + 0.002129N² − 1.3`（工程既有标定）与实测对比：

| 渲染帧数 | 公式预测 | 实测 | 偏差 |
|---|---|---|---|
| 124 | 132.1 s | 110.1 s | **+20 %** |
| 362 | 571.6 s | 555.0 s | +3 % |

公式在小帧数段偏高 20%（因为它拟合自骨架镜的大帧数数据，不含地板效应）。
**14.09 h 这个数字已经用「实渲帧数」代入公式，偏高 20% 于小镜 → 真实值可能更接近 12 h。**
无论如何，量级是 **10 h 以上，不是 6.57 h**。

### 反面清单（已实测否决，别再试）

- ❌ 「短镜每秒更便宜」→ 地板使 39 帧单价 67.7 s/镜秒，比 345 帧的 38.5 s/镜秒**更贵**。

- ❌ 按请求帧数估算总机时 → 漏掉 1.94 倍补齐开销。
