分镜 v2 审查 —— 与 v1 逐项对比

节奏重排版 v2（`v2-rhythm-cuts`，146 镜）vs v1 均分版（40 镜） · 2026-09-17 深夜

一句话结论

分镜本身通过审查 —— 不通过的是计价方式。

镜数不多，甚至偏少。v2 贴着参考片实测切点重排并做了贪心合并：参考片 94 / 103 个切点 （19.7 / 20.8 切/分），v2 压到 70 / 76 镜（14.7 / 15.4 切/分），比原片还少 26% 的切点。 反过来看，v1 的 4.0 切/分才是偏离原片节奏的那一版。

问题出在三份工作流模板把 length 固定成 362 帧（15.083 s）， 于是一条 2 秒的镜和一条 15 秒的镜花一样的钱。70 镜的窗口覆盖因此变成正片的 3.69 倍（v1 只有 1.01 倍）→ 两片 GPU 从 1.66 h 涨到 9.52 h。

而这个参数是节点原生的（`length` / step 17 / 栅格 `17n+5`）。 按镜帧数设置后，窗口覆盖回到 1.09 倍，两片落到 2.35–4.46 h；而且因为短窗的每帧成本更低，草稿档反而比 v1 更快。

二、钱的账：多出来的东西叫"窗口覆盖"

根因：模板把 length 写死成 362 帧

MiniMaxH3AudioConditioningT8 节点原生就有 length 输入：

# h3_t8/nodes.py:291
io.Int.Input("length", default=124, min=5, max=None, step=17,

但 v2 预览用的三份模板（`s16.api.json` / `api_s13.json` / `pg_B.api.json`）都沿用了历史值 362 帧， 且 `preview_flow.py` 里 `build_draft` / `build_direct` 只改 width/height、根本不设 length。 实测产物可以验证：

为什么 B 是个区间 —— 两个成本模型

模型① 贴实测：技能库里有一组实测阶梯 `17 s@124帧 / 43 s@243帧 / 73 s@362帧`（草稿档，同卡同 seed），log-log 拟合得 t = 0.024 × n^1.362（校验 17.1 / 42.6 / 73.4）。关键含义：每帧成本随时长上升 （0.137 → 0.177 → 0.202 s/帧），所以短窗口更划算。此模型下 B = 2.35 h。

模型② 线性保守：假设"每镜固定开销 25 s + 采样随帧数线性"， 上界取 `25 + 49×(n/362)`。此模型下 B = 4.46 h，是悲观的上界。

⚠ 两个模型都在 124 帧以下外推（v2 平均只有 98 帧）， 项目自己标过"未直接实测"。真实值大概率落在区间里、更接近模型①，但 在单镜验证之前， 排期请按 4.46 h 这个上界走。

三、审查发现（按严重度）

P0length 未按镜帧数设置 → 窗口覆盖 3.69×，白烧 5 h

证据：模板 + `preview_flow.py` 均不设 length；三镜产物全为 362 帧。 两片生成 52 852 帧、进成片 13 993 帧（利用率 26.5%），弃掉约 27 分钟素材。 这是本轮唯一"必须改"的一项，且零依赖。

P0抽检伪字幕率不支持 146 镜的乐观排期

三镜预览抽检 1 镜（片2 镜03）出现画面中下部乱码伪字幕 （`_review/v2_preview/README.md` 已记录），需过 `check_no_text.py` OCR 门重抽 seed。 镜数从 40 涨到 146，重抽次数同比例上涨：若 30% 镜需重抽一次 → A 档 9.52 h 变 12.4 h，B 档 4.46 h 变 5.8 h。样本仅 3 镜，不当比率用，但排期要留这个上行空间。

P126 个 ref2va 直出 768 吃掉近一半成本

片1 12 镜 / 7 572 s（占 47%），片2 14 镜 / 8 834 s（占 49%）。 631 s/镜 = 两阶段 149.6 s 的 4.2 倍。策略有依据（LTX 精修会重画包装印刷，产品镜不敢走精修）， 但它在 Mode B 下也会跟着掉到约 1/3，是降本第二块。

P1120 镜 T2V 的 ref_images 是空的 → 一致性 = 146 次摇号

`ref_images` 分布：片1 只有 12 镜、片2 只有 14 镜带参考图， 全是产品图（`_refs/prod_P2_white.png`）；其余 120 镜为空数组，人物外观纯靠 prompt 文本形容。 这不是 v2 引入的（v1 就被抱怨过"人物随便变"），但镜数 3.65× 把暴露面同步放大。 缓解选项：角色定妆照常驻 `ref_images`（节点支持最多 9 张）→ 需单镜验证能否与产品图共存。

P227% 的镜是"可并不可并都行"的碎切

相邻两镜同场景 + 同角色集且合计 ≤12 s 的： 片1 19 对、片2 20 对（70→51、76→56，合计 146→107）。 ⚠ 合并会丢硬切（一个窗口只能出一条连续 take，中途切就是跳切）。 所以这不是"该不该"，是"哪几对换掉硬切不心疼" —— 建议只并原片里靠近同机位同动作的短切。

四、Mode B 现在就能开（不用装任何东西）

栅格是 17n+5：5, 22, 39, 56, 73, 90, 107, 124 … 345, 362。 把每镜 frames 向上 snap 到最近的栅格值（多余 ≤17 帧 = 0.7 s，后期裁掉）：

镜1   78f →  90f (3.750s)     镜4   94f → 107f (4.458s)
镜2   48f →  56f (2.333s)     镜3  229f → 243f (10.125s)

# 工作流里只加这一行（preview_flow.py 的 build_draft / build_direct 同理）
wf["6"]["inputs"]["length"] = 90   # 原来没有这一行，节点吃默认 362
但必须先做「单镜验证」再排期 —— `STORYBOARD.md` 执行注意第 3 条自己规定了 「Mode B = `h3_length` 按镜帧数（成本近似线性降）需先单镜验证，验证前不得按此排期」。

验收四问：① 短窗（如 90 帧）能否正常出片、不崩结构； ② 画质与 362 帧版是否同档；③ `audio_mode=lock_source` 在短窗下音轨是否仍对齐； ④ 精修段吃短草稿时，输出帧数与时长是否仍匹配（LTX `frame_policy=trim_to_8n_plus_1` 会把 90 裁成 89 帧 = 3.708 s，字幕时间轴要跟着走 → 这是最容易漏的一条）。
