给 H3 喂产品图的两条路线 · 为什么「参考图」比「首帧锚定」更适合你 · 零 GPU 准备已全部就绪　｜　2026-09-17

结论：完全可行，是模型原生能力，不需要装任何新东西。

H3 的权重文件名就叫 minimax_h3_fl2va_*（fl2va = First-Last frame to Video+Audio）， 而我们一直在用的 MiniMaxH3AudioConditioningT8 节点是六合一统一节点—— 它同时支持 T2VA / I2VA / FL2VA / L2VA / Ref2VA / Hybrid，靠「你接了哪些输入」自动判断任务类型。 片 1 那 20 镜全是纯文生，图条件槽从头到尾空着 —— 这才是「产品的样子不对」的根因，不是参数没调好。

一、先分清两条路线：关键帧 ≠ 参考图

这是整件事里最容易被混淆、也最关键的一点。两者都能把产品图喂给模型，但机制完全不同：

对比项 FL2VA · 关键帧（first_frame / last_frame） Ref2VA · 参考图（ref_images）
在图里占位置吗 占。它就是你视频的第 0 帧或末帧，直接成为画面 不占。它不成为任何一帧，只「引导身份/外观」
产品能出现在哪些时段 只能 t=0 或 t=末中间完全没有 任意时段开头/中段/结尾都行
分辨率要求 必须与目标画布同比例（384×672） 可用自己的分辨率，节点按 ref_image_size 换算
能喂几张 最多 2 张（首 + 尾） 最多 9 张图 / 3 视频 / 3 音频
prompt 怎么写 「从首帧开始，只做以下动作」——端点图管「是什么」 「保持 <Picture 1> 的产品身份」——参考图管「是什么」
能力边界 两者可叠加 即 Hybrid：首帧锁死构图 + 参考图管产品身份，节点本身支持，不用额外装东西

为什么这条区别对你的片至关重要：上一轮我判断「镜 15 用不了」—— 因为那个镜里产品只在 6～10.5 秒的中段出现，而关键帧只能锁第 0 帧或末帧，两头都没有产品。 Ref2VA 把这个问题直接消掉了：参考图不占帧位，产品出现在第几秒都不影响，模型照样按参考图渲染。 于是从「3 个产品镜只有 1 个能用」变成 全部可用。

二、四条路线，逐个产品镜该怎么走

① T2VA 纯文生 片1 现状

完全不接图。产品长什么样，全靠 prompt 里那句「袋面空白无字」——模型只能自己编一个红壳。 这就是当前产品不对的根因。

② FL2VA 首帧锚定 已就绪 · 镜18

用 make_first_frame.py 把真产品图透视合成进原镜的 t=0 帧，接 first_frame 槽。 适合「产品在镜头的开头就出现」的镜。透视/光影/材质天然一致。

③ Ref2VA 参考图 正解 · 镜13/15

把产品图接到 ref_images 槽，prompt 用 <Picture 1> 点名。 不占帧位 → 产品在任意时段都能锁，且不需要预先合成关键帧（省掉一整道人工标定工序）。 这是「拿产品图针对性生成」的标准答案，官方也把 Ref2VA 列为「主体绑定」的推荐模式而非 I2V。

④ Hybrid 混合 后续可选

首帧 + 参考图同时接。构图锁死 + 产品身份全程引导，要求最高。 同一个节点就支持，等单一机制验证通过后再上。

四、发现的一个隐患：那套 <Subject N> 标签从来没生效过

H3 的媒体标签规范是 <Picture N> / <Video N> / <Audio N>， 而我们的 prompt 从头到尾写的是 <Subject 1>～<Subject 5>、<Subject P>。

这个节点的 strict_prompt_tags 参数为 true，会严格校验媒体标签的编号连续性。 <Subject N> 不是 H3 认识的媒体标签，只是普通文本 —— 也就是说， 片 1 的角色一致性一直只靠那几段英文外貌描写在撑，标签本身没有起到「绑定某张参考图」的作用。 更关键的是：不引用 <Picture 1>，参考图接上了也不会被认领，等于白接。

已经在代码层做了三处加固：

  1. 新增 SP_REF 产品锚定块，用 <Picture 1> 指代产品参考图，并声明「参考图负责产品外观，文字只负责走位与运镜」（对齐官方 R2V 规范）。
  2. build.py 加了一道 认领校验：标了 ref=True 但 prompt 里没有 <Picture 1>，直接报错拒绝生成。
  3. 禁字铁律的措辞从「as it appears in the opening frame」泛化为「as it appears in the supplied reference image」，让关键帧与参考图两种来源共用同一版条款，终端校验锚点一字未减。

六、仍然待实测的三件事（我不打包票）

这三条只能等实例恢复后用真实运行来确认，我不做未经实测的承诺：

  1. Ref2VA 是否需要单独的 ref2va 权重。 我们本地只有 minimax_h3_fl2va_pruned_int8_convrot.safetensors。 线索是矛盾的：T8 节点文档说「六种任务是同一个联合音视频 latent，只是挂了不同的参考输入」， 暗示同一份权重就能跑；但另一个实现（RunningHub）明确按 FL2VA / Ref2VA 分区，说 FL2VA 节点不提供 Ref2VA 权重。 缓解：这个节点自带 Preflight 校验，采样前会检查「模型/尺寸/帧数/音频/参考数量/视频时长」契约， 不合规会明确报错而不是静默出错。所以最坏情况是「报错要下权重」，不会悄悄跑出废片。
  2. ref_images 的真实槽索引是不是 8。 目前是按模板实测顺序 + 节点文档推出的，probe 一跑就定论。
  3. 多张参考图共用一个槽的行为。 文档说最多 9 图，但 ComfyUI 里「一个输入槽接多条线」的语义需要实跑确认。 建议先单图跑通，再加第二张 —— 而且官方也提醒「过多重叠的参考反而会削弱指令跟随」，单张往往更好。

七、验收标准（拉回片子后逐条过）

  • 袋面印刷是「鲍汁红烧酱料 / 佐味纪 / PICC / 建议零售价 8 元/包 / 净含量 80 克」真字，不是乱码也不是空白

推广到全部产品镜

验证通过后，给产品镜统一加 ref=True + 复用同一张 <Picture 1> 参考图即可。同一张参考图意味着跨镜产品外观会自动趋同， 这正是当前「产品每个镜长得都不太一样」的根治办法。
