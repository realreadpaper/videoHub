## 1. 为什么改这一项

Stage2 精修工作流的**最后一步**用 `MiniMaxH3SolEngineTAEHVDecodeT8Advanced` 解码。

TAEHV 是 ComfyUI 里的「微型视频自编码器」（Tiny AutoEncoder for Video），为**快速预览**设计，解码质量明显低于完整 VAE。

而完整 VAE（`ltx-2.5-video-vae-conv-bf16.safetensors`）**其实已经作为 VAELoader 加载在工作流里了**，却只被 `VAEEncode` 用于编码侧，解码侧根本没接。

> 等于：22B 模型 + 3 步精修辛苦算出来的 latent，在最后一步被一个预览级解码器糊掉了。

**外部佐证**：对成片做「下采样往返 PSNR 探针」，672px 往返高达 **49.95 dB**，意味着 1344×768 里几乎没有超过 672px 的真实高频——细节就是在解码环节丢的。（正常实拍 1080p 此测试通常只有 30~35 dB。）

**这是所有画质优化项里唯一「无损」的一项**：不改模型行为、不改提示词、不改步数，纯粹把已经算出来的信息完整还原。代价约 +7 分钟／8 镜。

三片脚本改完后逻辑完全一致（diff 只剩片名、SEED、输出文件名）。

### 补丁具体做了什么

1. 节点 17 的 `type` 从 `MiniMaxH3SolEngineTAEHVDecodeT8Advanced` 换成 `VAEDecode`
2. `samples` **沿用原 latent 连线**（上游仍是 SamplerCustomAdvanced）
3. 新增一条 `vae` 连线：节点 4 `VAELoader[0]` → 节点 17
4. `IMAGE` 输出槽 0 类型不变，**下游连线原样保留**（节点 18 OutputTrim 不受影响）
5. 原 `taehv` 连线回收（否则留下悬空 link）
6. 节点 25 `TAEHVLoader` 设为 `mode=4`（bypass），省一次权重加载

**未改动任何其他节点。** 已用 mock 工作流做 21 项逐条断言验证，全通过；另测了 `VAEDecodeTiled` 与 API 格式两条代码路径。

## 4. 画质怎么量化验收

不要凭肉眼。用探针：

```bash
cd /tmp && ffmpeg -y -i shot01.mp4 -vf "select=eq(n\,180)" -frames:v 1 o.png
ffmpeg -y -i o.png -vf "scale=672:384:flags=bicubic,scale=1344:768:flags=bicubic" d.png
ffmpeg -i d.png -i o.png -lavfi psnr -f null - 2>&1 | grep average
```

**判读**：改动生效的话，672px 往返 PSNR 应该**从 49.95 dB 明显下降**（往 40 甚至更低走）。下降 = 画面真的有了更多高频细节。

如果测出来还是 49~50 dB，说明 A1 没生效——回去查是不是 `--keep-taehv` 被误加、或补丁工作流没被同步上去。

## 6. 前提与边界

- **本次只做 A1**。A3（靶面提到 1920×1088）、dense 注意力、A5（编码 CRF）、B 组（音画同步）均未实施。
