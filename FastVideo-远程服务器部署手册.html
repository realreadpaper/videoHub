FastVideo 远程服务器部署手册

在远程 GPU 服务器上从零跑到对外提供视频生成服务。逐条命令，可直接复制。基于 hao-ai-lab/FastVideo main 分支 commit 9b0e57fe 核对。

远程 Linux 服务器 SSH 隧道接入 单卡 4090 路径 OpenAI 兼容 API 不烧字幕，产物外挂

0先说清楚：远程跑和本地跑差在哪

远程服务器上跑 GPU 推理，真正的难点从来不是显卡——是进程会死、端口不通、文件搬不回来这三件事。本地跑你可能一辈子不会遇到，远程跑第一天就会撞上。

问题本地会怎样远程会怎样解法
进程存活 终端不关就没事 SSH 一断，进程收到 SIGHUP 直接死，跑了 40 分钟的生成白费 tmux / systemd（第 6 节）
端口可达 127.0.0.1 直接开浏览器 服务绑在服务器的 localhost，你的电脑够不着 SSH 端口转发（第 7 节）
文件搬运 本地目录直接读 产物在服务器上，几十 GB 权重在服务器上 rsync / HF 断点续传（第 4、9 节）
权重下载 可能本来就有缓存 服务器多半是干净盘，且国内机房访问 HF 经常不通 HF_HOME + 国内镜像（第 4 节）
磁盘规划 不太在意 云盘按量计费，下错模型几十 G 白烧 先核体积再下（第 4 节，有实测体积表）

整体链路长这样

1第一步：先给服务器做个体检

别急着装东西。先花两分钟确认这台机器能不能跑，能跑哪个量级——环境不匹配的话，后面所有步骤都是白费。

我写了个自检脚本，只读不改。两种送上服务器的方式：

方式 A：直接 scp 上去（推荐）

# 在你本地执行，把脚本传到服务器
scp fastvideo-doctor.sh 用户名@服务器IP:~/

# 到服务器上执行
ssh 用户名@服务器IP
bash ~/fastvideo-doctor.sh /data          # /data 换成你打算放权重的盘

方式 B：懒得传文件，直接贴

# 在服务器上执行这一条，得到最小版体检结论
nvidia-smi --query-gpu=name,memory.total,driver_version,compute_cap --format=csv && \
uname -s && python3 -V && free -g | head -2 && df -h /data | tail -1

看什么

指标必须满足不满足会怎样
操作系统Linux（或 WSL）macOS 完全没有 CUDA 路径，只能走另一条 MLX 分支
GPU 算力8.9 = 4090 / L40S 同架构低于 8.9 则 FP8 硬件加速不可用，性能明显打折
显存≥ 20 GB 才有讨论价值低于这个数，视频生成基本跑不动
Python3.10 – 3.123.13 会被拒——但用 uv 的话这条自动绕过，见第 3 节
磁盘可用≥ 40 GB 起，想上 FastH3 要 140 GB装到一半空间不够，权重得重下
内存≥ 64 GB 舒服逐层卸载要靠宿主内存做权重中转缓冲，太小会频繁换页

关于 Python 版本，有个能省你半小时的细节

官方要求 Python 3.10–3.12，而很多服务器的系统 Python 是 3.13。你不需要去动系统 Python——uv 会自己下载一个独立的 3.12 解释器放进虚拟环境，跟系统的那个完全隔离。所以这条限制实际上不构成障碍。

2代码怎么到服务器上

别用 scp 把整个仓库传上去——服务器上git clone更快、更干净，而且以后拉更新只要一条命令。

# 在服务器上执行
# ① 装 git（如果没有），Ubuntu/Debian 系：
sudo apt-get update && sudo apt-get install -y git

# ② 克隆（--depth 1 省时间，不要完整历史）
git clone --depth 1 https://github.com/hao-ai-lab/FastVideo.git ~/FastVideo
cd ~/FastVideo

如果服务器访问不了 GitHub

国内机房常见。按顺序试：

  1. 换 SSH 协议：git clone git@github.com:hao-ai-lab/FastVideo.git（配好 key 后通常更稳）
  2. 用镜像：git clone https://ghproxy.net/https://github.com/hao-ai-lab/FastVideo.git
  3. 兜底：本地下好打包传上去——tar czf fv.tgz FastVideo && scp fv.tgz 用户@IP:~/ && ssh 用户@IP 'tar xzf fv.tgz'

关于 submodule

仓库带 3 个 submodule（ThunderKittens、cutlass、VBench）。纯 Python 推理不需要它们——pip install 会从 PyPI 装预编译好的 fastvideo-kernel 轮子。只有你要从源码编译 CUDA 内核（想开 VSA 稀疏注意力）才需要：

git submodule update --init --recursive    # 约 1–2 GB，按需

3装环境：三条路线，挑一条

A · uv 直装
最轻，无 root 也基本能用。适合已有干净服务器的场景
约 10 分钟
B · Docker
依赖全打包好，环境隔离最干净。适合多项目共存的机器
约 15 分钟（含拉镜像）
C · 云平台模板
RunPod 等平台自带 FastVideo 镜像，开箱即用
约 5 分钟

路线 A：uv 直装（我推荐这条起步）

我把整个流程写成了脚本，幂等、可重复跑：

# 传到服务器后执行
scp fastvideo-remote-setup.sh 用户名@服务器IP:~/
ssh 用户名@服务器IP

bash ~/fastvideo-remote-setup.sh --dir ~/FastVideo --cuda 126
# CUDA 13 的机器把 --cuda 126 换成 --cuda 130
# 想顺带编译 VSA 内核加 --with-kernel（多花 5–10 分钟）

脚本做四件事：拉仓库 → 装 uv → 建 Python 3.12 环境 → 装 fastvideo，并把 HF 相关环境变量写进 ~/FastVideo/.fastvideo-env.sh。

手动版的等价命令，便于你理解每一步：

# 1) 装 uv
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"

# 2) 建环境（uv 自动拉 3.12，与系统 Python 无关）
cd ~/FastVideo
uv venv --python 3.12 --seed
source .venv/bin/activate

# 3) 装（cu126 对应 CUDA 12.6，CUDA 13 用 cu130）
UV_TORCH_BACKEND=cu126 uv pip install -e .

# 4) 可选：flash-attn，装了推理快一档
uv pip install flash-attn --no-build-isolation -v

# 5) 验证
python -c "import fastvideo; print('OK')"
python -c "import torch; print(torch.cuda.get_device_capability(0))"
# ↑ 4090 必须输出 (8, 9)。这个数字后面所有优化判断都基于它。

路线 B：Docker

# 拉官方开发镜像（CUDA 12.6 版）
docker pull ghcr.io/hao-ai-lab/fastvideo/fastvideo-dev:py3.12-latest

# 建两个目录：权重缓存 + 产物输出
mkdir -p ~/fastvideo_models ~/fastvideo_outputs

docker run --gpus all -it --rm \
  --name fastvideo \
  --shm-size=16g \
  -v ~/fastvideo_models:/root/.cache/huggingface \
  -v ~/fastvideo_outputs:/outputs \
  -v ~/FastVideo:/FastVideo \
  ghcr.io/hao-ai-lab/fastvideo/fastvideo-dev:py3.12-latest

# 进容器后，uv 环境在 /opt/venv 且已激活，落在 /FastVideo
cd /FastVideo && uv pip install -e .

三个必踩的 Docker 坑

  • --shm-size=16g 漏了必崩——Docker 默认共享内存只有 64 MB，多进程加载模型直接挂
  • 不挂 HF 缓存目录，容器一删几十 GB 权重全丢
  • CUDA 13 的机器要换镜像 tag：py3.12-cuda13.0.0-latest，同时安装时用 UV_TORCH_BACKEND=cu130

路线 C：云平台（RunPod 等）

官方专门写了云 GPU 指南。要点：租 Pod 时选 FastVideo / fastvideo-dev 模板（自带全部依赖和 Flash Attention），然后：

  • 务必挂持久卷到 /root/.cache 或 /models——权重 10–140 GB，每换一次机器重下纯属烧钱
  • 连接方式：ssh root@<pod-ip> -p <port> -i ~/.ssh/id_ed25519
  • 卷挂好后设 export HF_HOME=/models/huggingface 并写进 ~/.bashrc
  • 用完一定要 "Terminate" 再 "Delete"——只停不删，存储照样计费

4下载权重：先把体积搞清楚

这里有个大坑：模型名字里的参数量和下载体积完全不是一回事。我实测查了 HF 上的真实体积：

模型名字听起来实际下载许可4090 单卡
FastVideo/FastWan2.1-T2V-1.3B-Diffusers 1.3B 27.2 GB Apache-2.0 可行
Wan-AI/Wan2.2-TI2V-5B-Diffusers 5B 31.9 GB Apache-2.0 吃力
FastVideo/FastVideo-Minimax-FastH3-Preview-v0.2 H3 蒸馏版 137.7 GB MiniMax 社区许可 单卡不可行

"1.3B" 下下来 27 GB，是因为仓库里除了 DiT 主干还包含完整的 VAE、文本编码器（umt5-xxl 一个就 ~11 GB）等组件。按实际体积规划磁盘，别按参数量猜。

把缓存指到大盘

# 关键：权重默认落在 ~/.cache，很可能是个小系统盘
# 指到数据盘，避免系统盘被撑爆
export HF_HOME=/data/hf_cache
export HF_HUB_CACHE=/data/hf_cache
export TRANSFORMERS_CACHE=/data/hf_cache
export HF_HUB_ENABLE_HF_TRANSFER=1        # 多线程加速，快 3–5 倍

# 写进 ~/.bashrc 让它长期生效
echo 'export HF_HOME=/data/hf_cache' >> ~/.bashrc

国内服务器必看：走镜像

# 直连不通时加这一条
export HF_ENDPOINT=https://hf-mirror.com

# 也可以直接写进 shell 配置，长期生效
echo 'export HF_ENDPOINT=https://hf-mirror.com' >> ~/.bashrc

下载命令

# 先装 hf 命令行（新版 huggingface_hub 自带）
uv pip install "huggingface_hub[cli]" hf_transfer

# 下 4090 能跑的那个（27 GB）
hf download FastVideo/FastWan2.1-T2V-1.3B-Diffusers \
  --local-dir /data/models/FastWan2.1-T2V-1.3B

# 断了重跑同一条命令即可断点续传，不会重下
# 后台跑（大文件建议），日志写文件：
nohup hf download FastVideo/FastWan2.1-T2V-1.3B-Diffusers \
  --local-dir /data/models/FastWan2.1-T2V-1.3B > /data/hf_dl.log 2>&1 &
tail -f /data/hf_dl.log

5跑通第一支片

先验证环境，别一上来就调优。

cd ~/FastVideo && source .venv/bin/activate

# 最小验证：跑仓库自带的最简例子
python examples/inference/basic/basic.py

# 看产物落在哪
ls -lh outputs/ 2>/dev/null; ls -lh video_samples/ 2>/dev/null

然后上你的配置。我把针对这张卡的配置放在 fastvideo-configs/ 目录：

# 稳妥起步档：FP8 量化 + VSA 稀疏 0.8 + 逐层卸载，480P / 81 帧
FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN \
  fastvideo generate --config ~/FastVideo/fastvideo-configs/06-rtx4090-24gb-fp8-vsa.yaml

# 没编译 VSA 内核的话，换回通用后端
FASTVIDEO_ATTENTION_BACKEND=FLASH_ATTN \
  fastvideo generate --config ~/FastVideo/fastvideo-configs/06-rtx4090-24gb-fp8-vsa.yaml

第一次跑特别慢，是正常的

如果配置里开了 compile.enabled，第一次生成要花几十秒到几分钟建图——这是一次性成本，之后每个请求都受益。官方文档专门点名这是"最常见的错误结论来源"：别拿第一次的耗时当性能基线。

6保活：SSH 断了不能死

这是远程服务器上最容易吃亏的地方。一条 40 分钟的视频生成任务，因为你的笔记本合盖断网就全没了。

方案 1：tmux（首选）

# 装（如果没有）
sudo apt-get install -y tmux

# 开一个会话
tmux new -s fv

# 在里面正常干活，然后按 Ctrl+B 再按 D 脱离
# 此时进程继续跑，SSH 断线也不受影响

# 下次回来重新接上
tmux attach -t fv

# 看有哪些会话
tmux ls

tmux 里跑长任务的正确姿势，是会话 + 日志文件双保险：

# 在 tmux 里执行，同时把输出写进日志，方便事后翻
fastvideo generate --config xx.yaml 2>&1 | tee -a ~/run_$(date +%m%d_%H%M).log

方案 2：nohup（不想开 tmux 时）

nohup fastvideo serve --config serve.yaml > ~/serve.log 2>&1 &
echo $! > ~/serve.pid          # 记下进程号
tail -f ~/serve.log            # 看日志
kill $(cat ~/serve.pid)        # 停服务

方案 3：systemd（有 root，且要长期常驻）

# /etc/systemd/system/fastvideo.service
[Unit]
Description=FastVideo OpenAI-compatible server
After=network.target

[Service]
Type=simple
User=你的用户名
WorkingDirectory=/home/你的用户名/FastVideo
Environment="HF_HOME=/data/hf_cache"
Environment="FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN"
ExecStart=/home/你的用户名/FastVideo/.venv/bin/fastvideo serve --config /home/你的用户名/FastVideo/serve.yaml
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now fastvideo
sudo systemctl status fastvideo
journalctl -u fastvideo -f        # 看日志

7服务化：端口怎么打通

先起服务

# 关键：绑 127.0.0.1，不要绑 0.0.0.0
FASTVIDEO_ATTENTION_BACKEND=VIDEO_SPARSE_ATTN \
  fastvideo serve --config ~/FastVideo/fastvideo-configs/08-4090-serve-fastwan1.3b.yaml \
  --server.host 127.0.0.1 --server.port 8000

另开一个终端验证就绪：

curl --fail-with-body http://127.0.0.1:8000/health
# 模型加载完成后返回 {"status":"ok"}
# 返回 503 说明工作进程池挂了，看服务日志

然后在你自己的电脑上开隧道

官方文档对远程场景给的就是这个做法——"keep the server bound to loopback and forward the port"：

# 在你本地电脑执行（不是服务器上）
ssh -N -L 8000:127.0.0.1:8000 用户名@服务器IP

# 本地 8000 被占用的话，映射到别的口
ssh -N -L 8001:127.0.0.1:8000 用户名@服务器IP

# 保持稳定，加心跳（网络抖动时不容易掉）
ssh -N -L 8000:127.0.0.1:8000 \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  用户名@服务器IP

然后本地浏览器直接开 http://127.0.0.1:8000/playground/——就是你服务器上那个 H3 playground，跟本地跑一模一样。

为什么推荐隧道而不是直接开端口

  • 不用改云平台安全组，不用把端口暴露到公网
  • FastVideo 的 HTTP 服务没有任何鉴权——官方原话："客户端里的 key 只是 SDK 要求的占位符，不是服务端鉴权"
  • 隧道走 SSH 加密，等于白送一层认证

血的教训：不要图省事改成 0.0.0.0

把 --server.host 改成 0.0.0.0 并开放安全组，等于把一台 4090 挂在公网上给人白嫖。没有 API Key 校验，任何人扫到端口就能无限调你的卡。

确实需要对外提供服务的，必须套一层带鉴权的反向代理（Nginx / Caddy + Bearer Token），并在代理层做限流和来源限制。

8调用它：接口速查

服务起来后是一套 OpenAI 兼容的 REST 接口，现有 OpenAI SDK 客户端改个 base_url 就能用，不用写适配层。

操作端点
服务健康检查GET /health
列出已加载模型GET /v1/models
提交异步任务POST /v1/videos
同步出片，直接返回 MP4POST /v1/videos/sync
查询任务状态GET /v1/videos/{id}
下载产物GET /v1/videos/{id}/content
删除任务与产物DELETE /v1/videos/{id}
H3 专用网页界面GET /playground/

最快的一次调用（curl）

# 同步出片：一次 POST 直接拿回 MP4 文件
curl -s -X POST http://127.0.0.1:8000/v1/videos/sync \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "fastwan21-1.3b",
    "prompt": "A fox runs through fresh snow, cinematic lighting",
    "size": "832x480",
    "num_frames": 81,
    "fps": 16,
    "seed": 1024
  }' --output out.mp4

# 响应头里有耗时和峰值显存，值得一看：
# X-Inference-Time-S / X-Peak-Memory-MB / X-Stage-Durations

用仓库自带的客户端（异步 + 轮询）

cd ~/FastVideo

# cURL 版
FASTVIDEO_BASE_URL=http://127.0.0.1:8000/v1 \
FASTVIDEO_MODEL=fastwan21-1.3b \
  bash examples/serving/clients/video.sh

# Python 版（需 openai==3.6.0，这是官方测过的版本）
uv pip install openai==3.6.0
FASTVIDEO_BASE_URL=http://127.0.0.1:8000/v1 \
FASTVIDEO_MODEL=fastwan21-1.3b \
  python examples/serving/clients/video.py

异步接口的两个反直觉行为

  • 失败的任务返回 HTTP 200，body 里是 status: "failed" + error 对象——这样 SDK 的轮询能正常终止而不是当成网络错误重试。别只看状态码判断成败。
  • 轮询超时不会取消 GPU 执行。客户端 30 分钟超时了，任务可能还在跑。把打印出来的 job ID 存好，用它单独查。

压测：摸出这张卡的真实产能

# 服务起着，另开一个终端
fastvideo bench --dataset random --num-prompts 20 --port 8000 --max-concurrency 1

# 想要更真实的评测集
fastvideo bench --dataset vbench --num-prompts 20 --port 8000

这一步的产出是"单条出片耗时"和"每小时能出几条"——这两个数字决定了后面所有变现讨论有没有意义。

9产物怎么拿回来

服务端写文件的位置由 server.output_dir 决定，客户端不能指定路径，每个视频按请求 ID 存一个唯一文件。

# 方案 1：rsync 增量同步（推荐，断了能续）
rsync -avP --exclude='*.tmp' \
  用户名@服务器IP:/data/outputs/ ./server_outputs/

# 方案 2：只拉某个任务
scp 用户名@服务器IP:/data/outputs/<job_id>.mp4 ./

# 方案 3：产物太多不搬了，直接在服务器上后处理
# （比如 ffmpeg 拼接、转码、抽帧，都在服务器做完再拉成品）

一条链路习惯：产物在服务器上就完成封装

如果你的下游还有拼接、加 BGM、响度归一化这些步骤，在服务器上做完再回传。回传几十 GB 原始片段，比回传几个成品 MP4 慢得多，而且云盘出流量常常是要计费的。

请求被拒，报模型名不对 请求里的 model 必须等于 server.served_model_name 先用 GET /v1/models 查实际对外暴露的名字

11安全与变现边界

三条硬边界

1. 代码许可 ≠ 权重许可

FastVideo 代码是 Apache-2.0，但模型权重单独授权：FastWan / Wan 系列是 Apache-2.0 可商用；MiniMax H3 系列走 MiniMax 社区许可；Lucy Edit 明确非商用。拿代码做内部产品没问题，对外卖服务前必须逐张核对 model card。

2. HTTP 服务本身没有鉴权

别把端口裸奔到公网。要走公网必须套带 API Key 的反向代理，并做限流。

3. 精度不是无损的

官方自认"非对齐安全"。MiniMax-H3 在区域编译 vs eager 下：像素误差 20.247/255、PSNR 16.67 dB、SSIM 0.7108。FP4 余弦相似度约 0.99。如果你的业务对画面一致性极敏感，先小批量验片再上量。

变现路径（按落地难度排）

路径怎么做前置条件
自用内容生产
最快		 /v1/videos/sync 天生适合脚本批处理：一条 prompt 批量出 480P 镜头，喂进你的解说 / 短剧管线 先用 bench 测出"一小时能出几条"
私有化交付
中等		 客户自带卡，卖部署 + 调优 + 工作流打包 需要一套可复制的部署脚本（本次交付的脚本就是起点）
API 转售
最难		 对第三方提供生成接口 单卡产能低 + 必须过权重许可 + 必须自建鉴权与计费

12你现在该做的三件事

  1. 跑体检脚本，把 fastvideo-doctor.sh 传上去执行，确认 OS / 算力 / 显存 / 磁盘四项
  2. 跑安装脚本，fastvideo-remote-setup.sh 一条命令把环境建好
  3. 下 27 GB 那个模型先跑通，拿到第一支 MP4 和第一个耗时数字，再谈调优和变现
