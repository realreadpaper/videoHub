**结论：不用，理论上就该按真实时长生成。** 现在一律跑 362 帧满窗是模板把参数写死的配置问题，不是设计。

- 依据：node 6 `MiniMaxH3AudioConditioningT8` 的 `length` —— default **124**（5.17 s）、min 5、step 17，
  tooltip 原文 `"24fps; snapped up to the 17n+5 H3 grid"` → 短时长本就是节点原生一等公民。

  - 4.5 s 镜 = 14.1 + 16.6 = **31 s** → **快 4.8×**
- ★ 提醒口径：按 3 秒生成 ≠ 只花 3 秒（成本 ≈ N^1.36，非线性）。

## 逐镜重定时（三部曲 24 镜，15s 固定 → 11.375–15.042s 弹性）

- **病根**：不是 15s 太长，是"每镜都写死 15s"。H3 机制 = 给时间窗 + 三段 prompt 时间戳；
  三段写完窗口还剩时间，模型**不会停**，会无指令续演 → 各镜各编各的 = 强制割裂。
  **判定三标尺**：拍点数 / 台词量（5 字每秒）/ 主体是否运动（纯静态单主体撑不满 15s）。
  24 镜里只有 **6 镜**真撑得住满窗。
- ★★ **双重栅格（这次新算平的，比 length 那节更靠前）**：
  ① H3 `length` ∈ **17n+5**；② LTX `frame_policy` 默认 **`trim_to_8n_plus_1`**
  （已在 A100 `/object_info` 核实：*"Official route trims without adding frames"*）→ **只裁不补，向下取 8m+1**。
  10–15s 区间只剩 **8 个合法档**：226/243/260/277/294/311/328/345/362（H3 帧）→
  成片 9.375/10.042/10.708/**11.375/12.042/12.708/13.375/14.375★/15.042** s。

  其余各档被裁 1–7 帧 = 0.042–0.292s，剪辑无感但**字幕轴必须按裁后算**。

## 12:04 · pilot 正式点火（前两次空转的教训）

### ★ 事故 1 · wait_go 显存判定死锁 30 分钟
等待器把「显存 < 8GB」写进空闲判定 → 从 11:26 干等到 11:56 都没启动。
原因：**ComfyUI 跑完任务后不会自动释放权重**，会常驻 20~29 GB（v3 结束后实测
28801 MiB，同时 GPU 利用率 0%）。**显存高 ≠ 在忙。**
正解：空闲判定只用「v3 进程消失 + 队列空（连续两次）」，判定通过后**主动 POST /free**。
实测 free 效果：显存 28801 → 675 MiB，内存可用 6.9 GB → 59.4 GB（放出 52 GB）。

### ★ 事故 2 · `pkill -f wait_go.sh` 会把自己也杀了
执行它的 ssh bash -c 命令行里同样含 "wait_go.sh" 字符串 → 自杀 → ssh 断连且**无输出**，
看起来像"命令静默失败"。排查时用精确匹配：
`ps -eo pid,args --no-headers | awk '$2=="bash" && $3=="wait_go.sh"'`（注意 heredoc/双引号里 $ 要转义）。
同类：pgrep -f 也会匹配到自己。

### 结论
- 服务器 11:41 那次"宕机"其实**没重启**（12:00 复查 uptime 19:29 未变），只是 sshd/网络层断连；
  ping 通 + 22 关闭 ≠ 实例崩溃，也可能是 sshd 被打爆（当时内存只剩 6.9 GB）。
- 真正的隐患是**内存**：ComfyUI RSS 长期 56 GB / 64 GB，available 一度只剩 4.5 GB。
  每次点火前先 POST /free（连 RAM 一起放），不要叠加任务。
